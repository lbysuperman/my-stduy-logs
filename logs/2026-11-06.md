## 错题与卡点

- **生成过程｜概念混淆。** 最初把切词器当成回复 token 的生成者，也漏掉了已生成 token 会参与下一步预测。切词器负责输入编码，模型根据输入和已生成序列逐步生成，最终回答的 token 解码后进入 `content`。
- **响应字段｜取值路径不熟。** 能认出推理文本的用途，但旧脚本的 `response_text` 保存的是整个 HTTP 响应正文。要先解析 JSON，再沿 `choices → [0] → message → content` 找最终回答。本人明确表示这部分仍不熟。
- **RAG 数据流｜混淆应用层与模型内部。** 初稿把 token ID 当作检索产出，又把模型调用放在检索阶段。今天的脚本里，程序根据问题选出原文，拼接阶段产出请求，DeepSeek 生成回答。
- **Python 实现｜字典取值与条件判断。** `docs[None]` 在本题会触发 `KeyError`，`get()` 的默认文本要加引号。文件分享练习中，曾把读取 `owner` 写成赋值，并把 `!=` 写成 `=!`。修复时应先检查登录用户对目标文件的权限，再修改 `shared_with`。
- **项目复盘｜验收重点偏离。** `D9` 检查练的是通用输入校验，在这次 RAG 任务上拆得过细。两条 API 记录验证了手动选片下的问答链路。更有区分度的实验是保留原问题和规则，只去掉 `D1` 里的“9 点”，观察模型面对**相关但证据不足**的资料时怎么答。这个实验只讨论了设计，尚未运行。
